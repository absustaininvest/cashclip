Admin.tsx creates raw mailto: URLs from untrusted strings in two places: the CashClip user table uses href={\mailto:${u.email}`}atartifacts/absustain/src/pages/Admin.tsx:2703, and the inbox reply action useshref={`mailto:${selected.fromEmail}?subject=Re: ${encodeURIComponent(selected.subject)}`}atartifacts/absustain/src/pages/Admin.tsx:2252`. Neither value is URI-encoded before being inserted into the link.

Those values are attacker-controlled. For registered users, the server-side validator in artifacts/api-server/src/lib/emailValidation.ts:1-42 accepts any non-whitespace, non-@ characters in the local part, so reserved URI characters such as ?, #, &, and % are allowed. For inbound mail, artifacts/api-server/src/lib/inbox.ts:91-116 forwards from?.address from the IMAP envelope straight into fromEmail without URI encoding or normalization for safe use in a mailto: URL.

This means an attacker can supply an address shaped like victim%40company.com?bcc=attacker%40evil.test#@example.com. It passes the current regex, is stored/displayed by the admin UI, and when the operator clicks the mail link the browser/mail handler interprets the part after ? as mail headers instead of part of the address. In practice this can add attacker-controlled bcc, cc, subject, or body parameters to the compose window. The result is a low-complexity social-engineering primitive that can silently copy attacker recipients on operator replies or prefill deceptive content in outbound admin communications. React's HTML escaping does not mitigate this because the bug is in URI parsing, not HTML rendering.
