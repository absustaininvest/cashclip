The public PayPal webhook endpoint relies on in-memory rate limits that only apply inside a single replica, so an attacker can multiply their allowed traffic by hitting different autoscaled instances. That lets an internet user drive repeated expensive PayPal verification work and degrade payout webhook processing for legitimate traffic.

The project threat model already notes that memory-only abuse controls are not authoritative on an autoscaled fleet. Despite that, both the global /api limiter in artifacts/api-server/src/app.ts:124-143 and the webhook-specific limiter in artifacts/api-server/src/lib/webhookRateLimit.ts:5-58 use express-rate-limit's default in-process memory store. The comments in webhookRateLimit.ts correctly acknowledge that the effective fleet-wide budget becomes limit * replica_count, but the public PayPal webhook still depends on that limiter in artifacts/api-server/src/routes/cashclip.ts:1039-1057.

This matters because /api/paypal/webhook performs expensive work for any request with the expected header shape and valid JSON body. After basic header parsing, verifyPayPalWebhook() in artifacts/api-server/src/paypal.ts:178-236 fetches a PayPal OAuth access token and then calls PayPal's verify-webhook-signature API. An attacker does not need a valid PayPal signature to trigger this outbound work; they only need to send repeated POST requests containing the required PayPal-style headers and a JSON body. Since both the global limiter and the webhook limiter are replica-local, those requests can be spread across autoscaled replicas to exceed the intended cap.

In production this creates a concrete availability issue: a public attacker can force the service to spend CPU, connection slots, and outbound requests on bogus webhook verification attempts, while legitimate payout status callbacks compete for the same resources. The impact is especially relevant here because payout state transitions are money-moving operations; delaying or dropping real PayPal webhook handling can leave withdrawals stuck in paying, delay refunds/rejections, and increase operator load during payout incidents.

The exploit path is straightforward: continuously send syntactically valid POSTs to /api/paypal/webhook with paypal-transmission-id, paypal-transmission-time, paypal-cert-url, paypal-auth-algo, and paypal-transmission-sig headers plus a small JSON body. Each replica will independently accept traffic up to its local budget, and each accepted request will attempt outbound verification with PayPal. In an autoscaled deployment, that defeats the intended abuse ceiling and turns the webhook into a practical amplification point for denial of service.
