Parallel sponsored-visit claims can bypass the daily visit-count limit
Medium
Sponsored Visit Abuse
A user can send several sponsored-visit claim requests at the same time and get paid for more daily visits than the server intends to allow. This weakens the main anti-farming control on low-value campaigns and lets attackers turn one account into more paid visits than policy permits.

The per-account sponsored-visit count cap is enforced by a standalone SELECT COUNT(*) before settlement starts (artifacts/api-server/src/routes/cashclip.ts:3493-3521). That count is checked outside the later settlement transaction and before any lock is taken. The code then enters a transaction that serializes only the daily dollar-cap check by taking pg_advisory_xact_lock(hashtext(userId)) (artifacts/api-server/src/routes/cashclip.ts:3577-3599). There is no second check for the visit-count cap after the lock is acquired and no database constraint limiting daily row count in campaign_clicks.

This creates a classic race: if an attacker already has, for example, 9 settled visits and the configured account limit is 10, they can trigger multiple /api/earn/sponsored/visit requests in parallel against different campaigns. Every request can read acctCount = 9 in the unlocked preflight query and pass the cap check. Once they enter the transaction, the advisory lock only protects the monetary cap, not the visit-count policy, so each request can still insert its own campaign_clicks row and credit the account (artifacts/api-server/src/routes/cashclip.ts:3602-3657).

The impact is concrete because campaign rewards can be as low as $0.01 (artifacts/api-server/src/routes/cashclip.ts:1983-1984). In that configuration, the separate $1 daily money cap is much looser than the nominal 10-visit cap, so racing requests can raise one account from the intended 10 paid visits per day to dozens more, limited only by available campaigns and the dollar cap. That materially increases the return of automated farming and undermines advertiser spend controls.
