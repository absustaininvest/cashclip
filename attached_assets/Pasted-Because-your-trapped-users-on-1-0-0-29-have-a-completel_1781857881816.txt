Because your trapped users on 1.0.0 (29) have a completely different, older native layer than your current codebase at commit 4e099fa (version 1.1.0 (46)), you cannot just push the current 1.1.0 code to them. Doing so will try to force 1.1.0 logic onto a 1.0.0 native runtime, causing immediate app crashes.
To safely port the modern code fixes and improvements into a package that the 1.0.0 (29) native app can actually read, follow this targeted rescue procedure.



⏱️ The Strategy: A Retroactive Hotfix Branch

                     (Old Runtime)
[ 1.0.0 (29) ] ───> [ Hotfix Update ] <─── Backport fixes here!
                           ▲
                           │ (Git Cherry-Pick / Merge)
[ 1.1.0 (46) ] ────────────┘ 
(New Runtime, Commit 4e099fa)
Instead of modifying your main development line, you will temporarily step back to the 1.0.0 state, pull in the JS improvements from your current commit, and publish them targeting the old runtime signature.



🛠️ Step-by-Step Rescue Execution

1. Check out a Temporary Hotfix Branch
Navigate to your local repository. Find the git commit hash that represented your original 1.0.0 (29) release. Spin up a temporary branch from that point:

bash
git checkout -b hotfix/rescue-1.0.0 <ORIGINAL_1.0.0_COMMIT_HASH>
Use code with caution.


2. Pull the 1.1.0 Improvements Backwards
Now, port the JavaScript improvements from your modern version into this hotfix branch. You can bring over specific feature commits, or merge the changes from your modern commit:

bash
# Bring over the specific improvements from your modern production commit
git cherry-pick 4e099fa
Use code with caution.

Note: Only bring over JavaScript, asset, or styling changes. Do not pick any commits that added new native packages (modified package.json native items, ios/, or android/ directories).

3. Match the Trapped Runtime Signature
Open your app.json or app.config.js on this hotfix branch. Look at your runtimeVersion configuration:
* If it says {"policy": "appVersion"}, make sure the root version field matches exactly what version 1.0.0 (29) expected (likely "1.0.0").
* If you have since adopted fingerprints, delete the fingerprint policy on this branch and hardcode the exact string tag used by the 1.0.0 (29) build on your Expo dashboard (e.g., "runtimeVersion": "1.0.0").

4. Publish Directly to the Deployment Channel
Publish this updated package from your hotfix branch. You must direct it to the exact channel or branch where your 1.0.0 users are listening:

bash
eas update --branch production --message "Backporting 1.1.0 improvements to 1.0.0 runtime"
Use code with caution.




🎯 What Happens Next?
EAS will process the update and notice it matches the 1.0.0 runtime fingerprint/signature.
* The 1.0.0 (29) Users: Their devices will detect a new update matching their runtime. They will download it and finally receive the improvements without encountering a crash.
* The 1.1.0 (46) Users: Their devices will completely ignore this update because their native runtime signature expects the 1.1.0 target. They remain safe on your newest setup.
Once the dashboard shows the update has been processed successfully, you can switch your local terminal straight back to your modern work line (git checkout main) and delete the temporary hotfix branch.
